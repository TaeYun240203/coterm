# coterm v1 Design

## Goal

Build `coterm`, a lightweight Go CLI plus a minimal Codex skill that makes agents execute task commands in a user-visible shared tmux terminal instead of hidden shell sessions.

The user opens the shared terminal from Warp by running `coterm open` in the workspace. Agents execute commands only by invoking `coterm`; `coterm` manages tmux sessions, panes, command runners, cursor tracking, logs, and dangerous-command approval.

## V1 Scope

`coterm` v1 is a single Go binary. It does not run a daemon, does not expose an MCP server, and does not install or control software on remote hosts.

The v1 execution target is local to the workspace where `coterm` is invoked. Remote work is still possible when the user or agent starts SSH inside a shared tmux pane through `coterm run`, but `coterm` itself does not provide `--host`, SSH profile management, remote install, or remote tmux control.

Removed from v1:

- `coterm init`
- `coterm agent start`
- `--session`
- `--host`
- `coterm host add`
- `coterm host test`
- remote `coterm` installation
- remote coterm-to-coterm execution
- automatic Warp launching
- session isolation between agents

## User Model

Each workspace gets one shared tmux session. Multiple agents working in the same workspace may use the same tmux session and panes.

The user sees the session by opening a Warp tab in the workspace and running:

```bash
coterm open
```

`coterm open` attaches the current terminal to the workspace tmux session. It does not start Warp, use URI schemes, or manage native Warp panes. The visible pane layout is tmux's pane layout rendered inside Warp.

If an agent runs a command before the user has opened the session, `coterm run` still creates the tmux session and pane. The structured response includes:

```json
{
  "open_command": "coterm open"
}
```

The skill may tell the user to run `coterm open` when seeing that field.

## Workspace State

`coterm` stores private runtime state in the workspace:

```text
<workspace>/.coterm/
├── session.toml
├── panes.toml
├── clients/
├── logs/
├── cache/
│   └── commands/
└── config.toml
```

`coterm` automatically adds `.coterm/` to the workspace `.gitignore` when it first creates the directory.

Responsibilities:

- `session.toml`: tmux session name, creation time, workspace path.
- `panes.toml`: logical pane names and tmux pane IDs.
- `clients/`: client-specific cursor state.
- `logs/`: command logs in JSONL.
- `cache/commands/`: script payloads generated by `coterm run --stdin`.
- `config.toml`: workspace-local configuration, including full-access state.

Agents must not inspect, edit, create, summarize, or rely on files under `.coterm/` directly. These files are `coterm` runtime state. Agents use `coterm` commands to access terminal state.

`.coterm/` is not a security boundary. V1 assumes cooperative agents that follow the installed skill. Permission enforcement is performed by `coterm run` at runtime, not by trusting mutable files inside `.coterm/`.

## Public CLI

The public user-facing CLI is:

```bash
coterm open
coterm run [--client <id>] --pane <name> -- <command> ...
coterm run [--client <id>] --pane <name> --stdin
coterm run [--client <id>] --pane <name> --detach -- <command> ...
coterm sync [--client <id>]
coterm read [--client <id>] --pane <name>
coterm snapshot [--client <id>] --pane <name> [--lines <n>] [--bytes <n>]
coterm panes
coterm pane close --pane <name>
coterm export --format jsonl
coterm uninstall [--purge]
coterm debug
```

Hidden user-only CLI:

```bash
coterm full-access on
coterm full-access off
coterm full-access status
```

`full-access` is intentionally omitted from normal help, debug output, and the agent-facing skill.

## Pane Model

Recommended pane names:

```text
main1, main2
scratch1, scratch2
longrun1, longrun2
interactive1, interactive2
```

Agents should prefer recommended pane names, but custom pane names are allowed when they improve clarity. Custom names must match:

```text
^[a-z][a-z0-9_-]{0,31}$
```

Reserved names are blocked:

```text
permission
permission1
permission-*
```

`coterm run`, `read`, `sync`, `snapshot`, and `pane close` cannot target the internal permission pane.

If a requested pane does not exist, `coterm` creates it automatically. If the workspace tmux session does not exist, `coterm` creates it automatically.

Pane cleanup uses:

```bash
coterm pane close --pane <name>
```

Closing a pane requires user approval because it can destroy process state or terminal output. The internal permission pane cannot be closed.

## Execution Model

`coterm run` executes commands by injecting a short runner into a tmux pane. Go code uses structured process invocation for tmux control:

```go
exec.Command("tmux", args...)
```

`coterm` does not build shell strings to control tmux.

One-line commands:

```bash
coterm run --pane main1 -- npm test
```

Multiline or long commands:

```bash
coterm run --pane main1 --stdin
```

For `--stdin`, `coterm` reads the payload from stdin, saves it under `.coterm/cache/commands/<command_id>.sh`, and injects a short runner into tmux. The runner emits start and end markers plus the exit code.

Default `run` behavior waits for completion and returns the exit code plus output delta. Long-running commands use explicit detach:

```bash
coterm run --pane longrun1 --detach -- npm run dev
```

Detached runs inject the command and return immediately. The agent uses `coterm sync`, `read`, or `snapshot` to inspect later output.

## Client and Cursor Model

Cursor state is per client, not shared across agents. The tmux session is shared, but each client has independent read cursors.

`--client <id>` is optional on any command that reads or advances cursor state. If omitted, `coterm` creates a new `client_id` and returns it in JSON. The agent must reuse that `client_id` for later calls.

`client_id` is not a secret or security token. It is a cursor namespace.

Command differences:

```text
coterm sync
  Reads deltas from all non-internal panes for the client and advances those cursors.

coterm read --pane <name>
  Reads the delta from one pane for the client and advances only that pane cursor.

coterm snapshot --pane <name>
  Reads the current latest pane snapshot and resets that pane cursor to the bottom.
```

`snapshot` defaults to recent tail output rather than unlimited scrollback:

```text
lines: 400
bytes: 65536
```

If truncated, responses include `truncated: true` and indicate that truncation came from the head of the captured output.

## Structured Output

Commands that return state use JSON-friendly structured output. Representative shape:

```json
{
  "ok": true,
  "client_id": "cl_8f31c2",
  "pane": "main1",
  "command_id": "cmd_abc123",
  "exit_code": 0,
  "output_delta": "...",
  "changed_panes": ["main1"],
  "truncated": false,
  "next_cursor": "...",
  "external_changes_detected": true,
  "permission_required": false,
  "permission_denied": false,
  "permission_timed_out": false,
  "open_command": "coterm open"
}
```

Long output is truncated to protect agent context. Cursor behavior depends on the command:

- `sync` and `read` advance cursor for the returned delta.
- `snapshot` advances cursor to the latest pane position even when it returns only a tail.

## Permission Model

Dangerous command detection happens inside `coterm run` immediately before execution. Agent built-in permission systems are treated as a secondary safety net, not the primary enforcement layer.

Dangerous examples:

- file deletion
- broad globs
- overwrite-prone copy or move
- permission or ownership changes
- package removal
- destructive git commands

When a command requires approval, `coterm run` displays the request in the user-visible shared terminal and waits up to 10 minutes. The request shows action, workspace, target pane, command ID, and the full command or script body. If the user approves, the same `coterm run` call executes the command immediately in the target pane. If the user denies, presses Enter without approval, or the request times out, the command is not executed.

Permission implementation details are not exposed in the agent-facing skill. The skill does not mention permission panes or internal approval UI.

## Full Access

`full-access` is a hidden user-only escape hatch:

```bash
coterm full-access on
coterm full-access off
coterm full-access status
```

It is workspace-local and persistent. When enabled, dangerous-command filtering is disabled for that workspace until the user turns it off.

This command is intentionally excluded from:

- normal help
- `coterm debug`
- the agent-facing skill

## Logging and Export

Logs are stored in:

```text
.coterm/logs/*.jsonl
```

Each record includes:

- workspace
- client ID
- pane
- command ID
- command preview
- start time
- end time
- exit code
- output
- truncation status
- permission result

Secret redaction is enabled for:

- API keys
- tokens
- passwords
- `.env` style values
- SSH private key blocks

No external upload is performed.

Users can export logs with:

```bash
coterm export --format jsonl
```

The agent-facing skill only uses `export` when the user explicitly asks for logs or export.

## Debug

`coterm debug` is the sanctioned diagnostic command. Agents use it when `coterm` errors instead of inspecting tmux or `.coterm/` directly.

It reports high-level diagnostics:

- `coterm` version
- workspace path
- state directory path
- tmux availability and version
- session existence
- pane mapping summary
- client cursor summary
- `.gitignore` status for `.coterm/`
- log file count and size
- last `coterm` internal error
- warnings and safe next actions

It does not expose:

- internal permission pane names
- permission UI details
- raw tmux commands
- `.coterm/` file contents
- `full-access`

## Agent-Facing Skill

Skill name:

```text
coterm-shared-terminal
```

The skill is intentionally short and strict.

Top rule:

```markdown
You must execute commands only by invoking `coterm`.

No other executable may be invoked directly for the user's task. This
prohibition applies even if the executable is not listed in examples.

Do not directly run commands such as `npm`, `git`, `python`, `go`, `ssh`,
`tmux`, `cat`, `sed`, `rg`, `ls`, tests, builds, package managers, project
tools, or any other executable.

If any command is needed, run it through:

`coterm run --pane <pane> -- <command> ...`

The only executable you may invoke directly is `coterm`.
```

Allowed direct invocations are only:

- `coterm sync`
- `coterm run`
- `coterm read`
- `coterm snapshot`
- `coterm panes`
- `coterm pane close`
- `coterm debug`
- `coterm export` only when the user explicitly asks for logs or export

Workflow rules:

- Call `coterm sync` before every `coterm run`.
- Call `coterm sync` after every `coterm run`.
- Call `coterm sync` before final answer.
- Preserve and reuse the returned `client_id`.
- Choose a pane explicitly.
- Prefer recommended pane names.
- Use `--stdin` for multiline scripts.
- Do not inspect, edit, create, summarize, or rely on `.coterm/` files directly.
- If `coterm` errors, run only `coterm debug`.

The skill does not mention permission internals.

## Install and Uninstall

End users install prebuilt binaries. Go is not required on user machines.

Install script responsibilities:

- detect OS and architecture
- download the matching release binary
- install `coterm` to `~/.local/bin/coterm`
- install the skill to `~/.codex/skills/coterm-shared-terminal/`
- print PATH guidance if `~/.local/bin` is not on PATH

Uninstall:

```bash
coterm uninstall
coterm uninstall --purge
```

Default uninstall removes:

- `~/.local/bin/coterm`
- `~/.codex/skills/coterm-shared-terminal/`

`--purge` removes global install/cache data owned by `coterm`. It does not automatically delete every workspace `.coterm/` directory because those are distributed across projects and may contain useful logs. Workspace state removal can be handled later by an explicit workspace cleanup command.

## Design Notes

V1 prioritizes simplicity, visible execution, and strong agent instructions over hard isolation. The security model assumes cooperative agents that follow the installed skill. Strong isolation against malicious agents requires a future design with a daemon, separate OS identity, or another real privilege boundary.
